# Техническая архитектура Memories

Версия 0.1 · 17 октября 2026 года

Memories — игра для Windows от первого лица с исследованием, головоломками, сюжетными воспоминаниями и элементами RPG. Основной архитектурный паттерн — MVP. Зависимости связывает VContainer, ввод обрабатывает Unity Input System, асинхронные последовательности выполняет UniTask, изменения состояния передаёт R3.

Документ задаёт основу разработки и границы первой реализации. Согласованный стек и концепция перечислены отдельно от предлагаемого устройства систем. Имена будущих классов и папок служат ориентиром; их появление в документе не означает, что соответствующий код уже написан.

## Концепция и технические приоритеты

Героиня просыпается в незнакомом месте, не зная, что находится в загробном мире. Мир состоит из островов, висящих в пустоте: фрагментов комнат, домов, улиц и природы. Большая часть пространства погружена во тьму. Участки света служат ориентирами. Героиня использует фонарь и способности, решает головоломки и собирает осколки воспоминаний о значимых событиях своей жизни. Боя нет.

Архитектура должна поддерживать добавление новых взаимодействий, сохранение изменений мира и управление персонажем во время сюжетных эпизодов. Свет может быть частью представления и игровой механики; если механика требует проверки освещённости, её условия должны быть заданы явно, а не выводиться из яркости пикселей на экране.

Пример будущего игрового сценария: героиня находит воспоминание, просматривает эпизод, получает доступ к способности и применяет её к препятствию. Связь конкретного воспоминания с конкретной способностью определяется контентом; обязательная выдача способности за каждый фрагмент не предполагается.

## Предлагаемые границы MVP

| Элемент | Ответственность | Ограничение |
| --- | --- | --- |
| Model | Изменяемое состояние и игровые правила | Не хранит ссылки на сценовые объекты и не читает устройства ввода |
| View | Unity-представление: объекты сцены, свет, звук, UI | Не принимает решения о сюжетном прогрессе и доступности способностей |
| Presenter | Принимает команды, вызывает правила, обновляет View | Не ищет зависимости через глобальные объекты или контейнер |
| Unity-адаптер | Физика, камера, raycast и другие операции движка | Возвращает результат логике, не подменяя игровые правила |
| Сервис | Операция, общая для нескольких компонентов | Имеет конкретную ответственность и определённого владельца |

Model и Presenter реализуются обычными C#-классами. View и адаптеры движка могут быть MonoBehaviour. Предлагается отделить доменные модели от UnityEngine; координаты и другие типы движка допустимы в контрактах адаптеров и слое представления. Для небольшой первоначальной реализации это логические границы, а не требование создавать отдельную сборку для каждого слоя.

Пример фонаря: команда ввода поступает в FlashlightPresenter, тот проверяет доступность и меняет FlashlightModel. FlashlightView отображает состояние через Light и звук. Расход батареи, перегрев и прочие ограничения не вводятся без отдельного игрового решения.

Для движения предлагается отдельный PlayerMotor, который выполняет перемещение и обработку столкновений. PlayerPresenter передаёт ему намерение движения и разрешение на управление. Это сохраняет физику в Unity и не требует создавать Model и Presenter для каждого технического компонента.

Прямой вызов метода используется для команды с ожидаемым результатом. R3 используется для наблюдения за изменениями. Общая глобальная шина событий на первом этапе не требуется: связи между модулями проходят через небольшие явные контракты.

Созданы следующие Assembly Definitions. Стрелка зависимости означает, что сборка использует указанную сборку; обратная ссылка автоматически не появляется.

| Сборка | Расположение относительно Assets/_Project | Зависимости от кода проекта |
| --- | --- | --- |
| Memories.Contracts | Code/Contracts | Нет |
| Memories.Gameplay | Code | Contracts |
| Memories.Infrastructure | Code/Infrastructure | Contracts |
| Memories.Bootstrap | Code/Bootstrap | Contracts, Gameplay, Infrastructure |
| Memories.Editor | Code/Editor | Contracts, Gameplay, Infrastructure, Bootstrap |
| Memories.Tests.EditMode | Tests/EditMode | Contracts, Gameplay, Infrastructure, Bootstrap |
| Memories.Tests.PlayMode | Tests/PlayMode | Contracts, Gameplay, Infrastructure, Bootstrap |

Корневая сборка Gameplay охватывает Features и UI. Вложенные asmdef выделяют Contracts, Infrastructure, Bootstrap и Editor в самостоятельные сборки. Gameplay не зависит от Infrastructure. Editor и EditMode ограничены платформой Editor; обе тестовые сборки отмечены как Test Assemblies и требуют UNITY_INCLUDE_TESTS. При обычной сборке игры тесты не включаются.

Auto Referenced выключен: ссылки между сборками задаются явно. Override References включён, чтобы не подключать все NuGet DLL автоматически. R3.dll подключён к Contracts, Gameplay, Infrastructure и тестовым сборкам. UniTask доступен runtime-сборкам и тестам; R3.Unity — Gameplay, Infrastructure и тестам; Unity.InputSystem — Infrastructure; Unity.ugui — Gameplay; VContainer — Bootstrap. Новые ссылки добавляются по фактической необходимости. Unity-типы разрешены в контрактах адаптеров, но доменные модели по-прежнему не должны зависеть от сценовых объектов.

В Bootstrap реализован запуск приложения и владение областями жизни; в Tests/PlayMode добавлены проверки запуска и освобождения областей. Остальные сборки пока могут не содержать скриптов; предупреждения Unity о таких пустых сборках ожидаемы. Пустые папки представлены в Git своими .meta-файлами и восстанавливаются Unity при импорте.

## Реализованный Bootstrap

Точка входа — `Assets/_Project/Scenes/Bootstrap.unity`. Для проверки открыть эту сцену отдельно и нажать Play. Она содержит AppLifetimeScope; BootstrapEntryPoint запускается VContainer и через GameSession создаёт SessionLifetimeScope, загружает FirstPersonTest дополнительно и создаёт LocationLifetimeScope внутри загруженной сцены. Полигон становится активной сценой; Bootstrap остаётся загруженным. Прямой запуск FirstPersonTest открывает только полигон, без автоматического создания DI.

Bootstrap добавлен первым в EditorBuildSettings, FirstPersonTest — вторым. Существующая SampleScene сохранена в списке. Геометрия, камера и освещение полигона не изменены. Настройки ввода, сохранения, игровые состояния и контроллер игрока на этом этапе ещё не реализованы.

ApplicationContext, SessionContext и LocationContext задают идентификатор экземпляра и CancellationToken соответствующей области. Это технические объекты времени жизни, а не модели сюжетного прогресса. Состояние сессии регистрируется как Singleton в её контейнере и доступно локации тем же экземпляром. Регистрация игрового содержимого добавляется в Configure соответствующего LifetimeScope.

GameSession располагается в Bootstrap как координатор композиции. StartAsync запускает одну сессию с одной локацией; повторный или параллельный запуск отклоняется. EndAsync освобождает локацию, затем сессию, выгружает сцену и позволяет начать новую сессию. Область приложения при этом сохраняется. Переход между локациями внутри одной сессии будет добавлен отдельным этапом.

Unity-загрузка сцены завершается до обработки отмены: после отмены созданные области освобождаются, а загруженная сцена выгружается. Неизвестная или уже загруженная сцена отклоняется до создания сессии. Исключения автоматического запуска выводятся в Unity Console; интерфейс ошибки и повторной попытки пока отсутствует.

PlayMode-проверки находятся в BootstrapLifetimeTests и BootstrapSceneTests. Они проверяют иерархию DI, общий экземпляр состояния сессии, освобождение токенов, повторный запуск, отмену загрузки, недопустимый запуск и автоматический старт из Bootstrap-сцены. Все пять проверок прошли в отдельной копии проекта на Unity 6000.3.18f1 в batchmode; это проверка поведения, а не визуального качества или готовности Windows-сборки.

## Предлагаемые области жизни VContainer

| Область | Время жизни | Объекты |
| --- | --- | --- |
| AppLifetimeScope | От запуска до закрытия приложения | Настройки, сервис ввода, загрузка сцен, файловое хранилище сохранений |
| SessionLifetimeScope | От новой игры или загрузки до завершения сессии | Прогресс истории, найденные воспоминания, открытые способности, состояние мира |
| LocationLifetimeScope | Пока загружена игровая локация | Игрок, презентеры, взаимодействия, головоломки и игровой HUD |

Иерархия: App → Session → Location. Контейнер создаёт зависимости, но сами игровые классы не вызывают Resolve. Обычные C#-классы получают зависимости через конструктор; для MonoBehaviour используется регистрация сценовых объектов и внедрение зависимостей при сборке области.

Объекты общего состояния регистрируются как единственный экземпляр в области-владельце, доступный её потомкам. Например, регистрация прогресса сессии должна возвращать один и тот же экземпляр обеим последовательно загружаемым локациям. Нельзя механически регистрировать всё как Lifetime.Scoped: у VContainer этот режим может создавать отдельный экземпляр на дочернюю область. [Правила времени жизни VContainer](https://vcontainer.hadashikick.jp/scoping/lifetime-overview)

Долгоживущий сервис не хранит View или Presenter локации. Перед выгрузкой локации прекращаются её операции и подписки. Удаление LifetimeScope само по себе не гарантирует удаление всех зарегистрированных MonoBehaviour: сценовые объекты уничтожаются выгрузкой сцены либо своей иерархией владения. [Жизненный цикл сценовых объектов](https://vcontainer.hadashikick.jp/scoping/lifetime-overview)

## Предлагаемый запуск и переходы

Постоянная Bootstrap-сцена содержит корень приложения. Игровая локация загружается отдельно; переход между островами не уничтожает корень приложения и данные сессии. На первом этапе один остров или связанная группа островов может составлять одну локацию. Потоковая загрузка отдельных островов пока не требуется.

Последовательность запуска:

1. Создать AppLifetimeScope, прочитать настройки и подготовить ввод.
2. Начать новую сессию либо восстановить её данные из сохранения.
3. Загрузить локацию и создать LocationLifetimeScope с родителем сессии.
4. Применить сохранённое состояние объектов, установить игрока в точку появления.
5. Подключить презентеры и разрешить игровое управление.

Для первой версии предлагаются состояния приложения Boot, Loading, Playing и Error. Внутри Playing располагаются режимы Exploration, Paused и MemoryPlayback. Меню добавляется тогда, когда появляется соответствующий пользовательский сценарий.

Контекст перехода хранит предыдущий допустимый режим: закрытие паузы во время воспоминания возвращает к воспоминанию, а не к свободному исследованию. Во время Loading повторный запрос перехода отклоняется либо объединяется с текущим. Ошибка загрузки переводит приложение в определённое состояние восстановления, а не оставляет его без управления.

## Предлагаемая система ввода

InputService владеет экземпляром Input Actions и переключением карт. Игровые классы получают текущие значения движения и обзора, а также события отдельных действий через контракт IPlayerInput. Доступ к Keyboard.current или Mouse.current внутри презентеров не используется.

Unity Input System поддерживает карты действий в Input Action Asset. Их группировка позволяет отделить игровое управление от интерфейса. [Документация Input Actions](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.19/manual/ActionAssets.html)

Предлагаемые карты:

| Карта | Действия | Когда активна |
| --- | --- | --- |
| Gameplay | Move, Look, Interact, Flashlight, Ability | Свободное исследование |
| UI | Navigate, Submit, Cancel, Point, Click, Scroll | Меню и интерактивный интерфейс |
| System | Pause | Режимы, допускающие паузу; остаётся доступной для её закрытия |

Клавиатура и мышь — первоначальная схема управления. Назначения клавиш, геймпад, переназначение, бег, прыжок и приседание требуют отдельного решения. Наличие подобных действий в шаблонном asset не означает, что они включены в дизайн игры. В частности, существующее Attack не становится боевой механикой, а шаблонный Hold у Interact не фиксирует обязательное удержание кнопки.

Движение считывается в игровом цикле, дискретные команды обрабатываются однократно. Обзор учитывает разницу между перемещением мыши и отклонением стика; единое безусловное умножение обоих сигналов на deltaTime не закладывается в контракт.

Режим игры управляет картами ввода, видимостью курсора и его блокировкой. При потере фокуса сбрасываются удерживаемые значения. Пауза блокирует движение и взаимодействия; UI и переходы, которые должны работать во время паузы, используют независимое от timeScale время.

## Правила использования R3 и UniTask

R3 передаёт изменения доступности взаимодействия, состояния фонаря, прогресса и данных UI. Изменяемые свойства остаются у владельца; наружу передаются представления только для чтения. Подписками презентера владеет сам презентер и освобождает их в Dispose. Модель сессии не освобождается вместе с подписанным на неё интерфейсом локации.

В R3 OnErrorResume сообщает об ошибке без обязательного завершения потока, а OnCompleted может завершить его с результатом ошибки. Для игрового кода требуется явная политика обработки: ошибка отображается в диагностике, критическая операция прекращается. Продолжение потока не означает успешность неудавшейся команды. ObservableTracker используется при проверке оставшихся подписок. [Поведение и диагностика R3](https://github.com/Cysharp/R3#core-interface)

UniTask используется для загрузки локаций, переходов, показа воспоминаний и других операций с завершением. Методы таких операций принимают CancellationToken и передают его дальше. Владелец операции определяет время жизни токена: приложение, сессия, локация или конкретный показ воспоминания. Отмена не подменяется успешным выполнением. [Отмена в UniTask](https://github.com/Cysharp/UniTask#cancellation-and-exception-handling)

Операции возвращают UniTask или UniTask<T>. Запуск без ожидания допускается только на границе событий с обработкой исключений. Освобождение блокировки управления выполняется также при отмене и ошибке. Повторное нажатие не должно одновременно запускать два показа одного воспоминания или два перехода.

## Предлагаемые игровые модули

| Модуль | Ответственность | Важная граница |
| --- | --- | --- |
| Player | Намерение движения, обзор, разрешение управления | Физику выполняет PlayerMotor |
| Interaction | Поиск объекта в направлении взгляда, доступность, команда взаимодействия | Дальность и препятствия учитываются; результат проверяется повторно при действии |
| Flashlight | Доступность и включение фонаря | Визуальные параметры задаются конфигурацией |
| Abilities | Открытые способности, проверка и выполнение применения | Конкретные способности и ограничения ещё не определены |
| Memories | Уникальные фрагменты, факт получения, запуск представления | Повторное получение не дублирует прогресс |
| Puzzles | Локальные условия и состояние головоломки | Завершение записывается в состояние мира |
| Story | Сюжетные факты и условия открытия контента | UI и сценовые объекты не служат источником истины |
| UI | Подсказка взаимодействия, пауза, показ данных | Изменяет игру только через команды |

Один объект взаимодействия предоставляет понятную подсказку, доступность и операцию выполнения. Взаимодействие с дверью не обязано знать устройство системы воспоминаний: оно обращается к необходимому условию прогресса через контракт.

Для первой головоломки достаточно конкретной реализации. Универсальный граф квестов, редактор диалогов, дерево навыков и полноценный инвентарь не входят в начальную основу. Они появляются после определения соответствующих игровых механик.

## Предлагаемые конфигурации и сохранения

ScriptableObject хранит авторские данные: параметры движения, описание способности, описание воспоминания, идентификаторы и ссылки на представление. Изменяемые данные прохождения находятся в моделях сессии. Получение воспоминания не изменяет исходный asset.

Объекты сохраняемого мира получают стабильные идентификаторы. Имена GameObject, путь в иерархии и Unity InstanceID не используются как ключи сохранения. Для объектов разных локаций ключ включает идентификатор локации и объекта; копирование объекта требует проверки уникальности.

Предлагаемый состав SaveData:

| Поле | Содержание |
| --- | --- |
| SchemaVersion | Версия формата для миграций |
| LocationId и SpawnPointId | Локация и безопасная точка восстановления |
| CollectedMemoryIds | Уникальные найденные воспоминания |
| UnlockedAbilityIds | Открытые способности |
| StoryFacts | Сюжетные факты |
| WorldObjectStates | Состояния дверей, механизмов и головоломок |

Сохранение содержит простые сериализуемые данные без MonoBehaviour, ссылок на сцену и реактивных подписок. Формат первого прототипа предлагается сделать JSON; конкретный сериализатор выбирается при реализации. Настройки пользователя хранятся отдельно от прогресса.

Запись выполняется через временный файл с заменой основного после успешного завершения и сохранением предыдущей рабочей копии. Одновременные записи исключаются. Повреждённое сохранение и неизвестная версия обрабатываются явно, без молчаливого уничтожения данных. Загрузка применяет данные до разрешения управления игроком.

Момент фиксации найденного воспоминания, автосохранение, ручные слоты и восстановление после падения с острова пока не определены. До их выбора не следует связывать сохранение с конкретным визуальным эффектом или длительностью сюжетного эпизода.

## План первой реализации

| Этап | Результат | Критерий готовности |
| --- | --- | --- |
| 1. Зависимости | VContainer, UniTask, R3 с Unity-интеграцией и фиксированными версиями | Проект компилируется и запускается; источники пакетов воспроизводимы |
| 2. Основа | Bootstrap, области жизни, состояния, InputService | Повторный запуск и смена тестовой локации не дублируют сервисы и подписки |
| 3. Игрок | MVP для движения и обзора, PlayerMotor | Можно перемещаться по полигону, проверять проходы, лестницу и пандус; ввод блокируется на паузе |
| 4. Взаимодействие | Выбор цели, подсказка и один тестовый объект | Объект за препятствием или вне дальности недоступен; одно действие даёт один результат |
| 5. Фонарь | Model, View, Presenter | Включение корректно отражается в модели и представлении |
| 6. Воспоминание | Один фрагмент и тестовый показ | Получение уникально; после завершения, отмены или ошибки управление корректно восстановлено |
| 7. Прогресс | Минимальная запись и восстановление | После перезапуска найденный фрагмент и изменённый объект восстанавливаются |

Этапы 1–3 составляют первичную техническую основу. Этап 1 выполнен; в этапе 2 реализованы Bootstrap и области жизни, ввод и состояния остаются следующими задачами. Этапы 4–7 проверят основу на небольшом законченном игровом сценарии.

Для MVP игрока сначала выбирается способ перемещения. Предлагаемый кандидат — CharacterController для управляемого движения от первого лица; окончательное решение зависит от требований к прыжкам, наклонам, платформам и взаимодействию с физическими объектами.

## Проверка архитектуры

EditMode-проверки покрывают правила получения воспоминаний, доступность способностей, восстановление данных и переходы состояний. PlayMode-проверки покрывают подключение зависимостей, переключение ввода и освобождение объектов локации. Производительность и ощущения от движения проверяются на полигоне и в Windows-сборке, а не выводятся из выбора библиотек.

Для каждой функциональности проверяются её обычное завершение, повторный вызов и прерывание сменой локации. Отдельно проверяется отсутствие обращений к уничтоженным View и роста числа активных подписок после повторного входа в локацию. Автоматизируются существенные правила и регрессии; визуальные ощущения и удобство управления остаются предметом ручной проверки.

У первой Windows-сборки проверяются запуск вне редактора, клавиатура и мышь, пауза, потеря фокуса и повторное открытие приложения. Целевые FPS, разрешение и минимальное оборудование ещё не заданы.

## Решения для следующих этапов

| Решение | Когда необходимо |
| --- | --- |

| Падение с островов и безопасное восстановление | До первой островной локации |
| Условия сохранения и число слотов | До пользовательского сохранения |
| Геймпад и переназначение управления | До расширения схем ввода |
| Локализация и способ авторинга текста | До массового наполнения сюжетным контентом |
| Целевое оборудование и бюджет производительности | До производства финальных локаций |

## Правила изменений проекта

Работа ограничивается текущей задачей. Перед редактированием файла с пользовательскими изменениями проверяется diff. Соседние исправления, рефакторинг и переносы assets не выполняются попутно. Изменения сцен, prefab, сериализованных ссылок и оформления выполняются только в рамках явно требующей их задачи.

Техническая документация обновляется при изменении принятого решения или фактического состояния реализации. Предложение становится принятым решением после согласования либо реализации в рамках явно поставленной задачи; сама запись предложения не является разрешением менять проект.
